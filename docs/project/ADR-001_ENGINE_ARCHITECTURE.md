# ADR-001: Godot 4.7.2와 독립 전투 코어로 MVP 개발

결정일: 2026-09-26 KST.
상태: SELECTED_FOR_MVP. 사용자가 지금 엔진/구조를 선택하도록 요청하여 내린 기술 결정이다. 사용자 플레이 승인이나 성능 검증 완료를 뜻하지 않는다.

## 1. 결정

- 새 개발 기준: Godot 4.7.2-stable, Windows x86_64 일반판, 정적 타입 GDScript.
- 첫 렌더러: Compatibility. 첫 검증 플랫폼: Windows. 첫 월드 640x360, 표시 창 1280x720, 정수 배율과 최근접 필터.
- 기존 Godot 4.3 프로젝트는 재현용으로 그대로 보존한다. 자동 업그레이드하지 않는다.
- 기존 전투 코어를 상속/확장하여 계속 누적하지 않는다. 별도 프로젝트에서 전투/표현/데이터 책임을 나누어 재작성한다.
- Unity/GameMaker 병렬 프로토타입은 지금 만들지 않는다. 엔진 선택을 또다시 백업 확인 뒤로 미루지 않는다.
- 새 프로젝트는 기존 user://, SaveManager, 원본 장면, 실제 save.json과 독립적이다. 원본에 접근하지 않는 새 코드 제작은 로컬 백업 확인과 병렬로 진행 가능하다.
- 기존 저장의 덮어쓰기/이관/복원/새 엔진으로 원본 열기는 여전히 별도 안전 검증 대상이다. 업로드한 save.json 한 개를 사용자 PC 전체의 검증 백업으로 간주하지 않는다.

이 기록은 ENGINE_GATE.md, E0_ACCEPTANCE.md, 이전 HANDOFF의 '백업 완료 전 E0 제작 금지'와 '양 엔진 실측 후에만 선택' 절차를 교체한다. 기존 전투/소유권/라이선스/실행 검증 계약은 유지한다. 선택 이후 E0는 선택한 구조를 실제로 검증하는 단계다.

## 2. 선택 근거와 다른 선택을 하지 않은 이유

현재 요구의 중심은 2D 픽셀 자동전투, 짧은 원정의 성장 선택, 장비/어픽스와 장기 성장이다. 공식 Godot 문서에는 AnimatedSprite2D/SpriteFrames/AnimationPlayer를 이용한 프레임 애니메이션, Resource 기반 데이터, 책임이 분리된 장면 구성 방법이 있다. Compatibility는 고급 렌더 기능을 요구하지 않는 2D 게임의 출발점으로 공식 안내된다. [S2-S5]

프로젝트 PR #17에서 확인한 정지 원화, 이중 무기 표현, 타격 타이밍 문제는 엔진 기능 부재를 증명하지 않는다. 따라서 이를 이유로 Unity 전환 비용을 추가하지 않는 것이 이번 기술 판단이다. 기존 GDScript 분량이 아까워서 유지하는 결정이 아니다. 기존 코드가 하나도 없다는 조건에서도 이 MVP와 채팅/GitHub 기반 작업에는 같은 선택을 권한다.

GDScript/.tscn/.tres 중심으로 변경과 재현 정보를 저장소에 남긴다. .NET, Unity Hub, 외부 플러그인, 복잡한 의존성 주입 프레임워크는 초기 요구가 아니다. C#을 금지하는 것이 아니라 이번 MVP에서 추가하지 않는 선택이다.

Unity가 2D 구현을 못해서 제외하는 것이 아니다. 현재 필수 Unity 전용 도구/광고/결제/배포 요구가 정해진 것은 아니며, 아직 엔진 간 동일 조건 성능 비교도 하지 않았다. 'Godot이 Unity보다 빠르다'는 실측 결론은 없다. GameMaker 역시 레퍼런스와 엔진 이름을 맞추기 위해 도입하지 않는다.

공식 빌드 저장소의 4.7.2-stable 릴리스는 draft=false, prerelease=false, published_at=2026-08-18로 조회했다. 일반 다운로드 페이지 캐시가 4.7.1을 표시해 릴리스 자체로 존재를 재확인했다. 여기서는 '언제나 최신 버전'이 아니라 재현 가능한 4.7.2를 고정한다. 기존 4.3 문서는 지원 종료로 안내된다. [S1, S6]

## 3. 구조: 작은 단일 게임, 책임 분리

계획된 독립 프로젝트 경로: experiments/e0-godot/project.godot. 이 ADR 작성 시 아직 생성하지 않았다.

```text
GameRoot (조립과 수명만 관리)
  CombatSession (실행 중인 전투와 시뮬레이션 시간)
    ActorState / ActorController (상태와 자동 행동)
    CombatResolver (대상 검증, 피해, 사망)
    ProjectileSystem (실제 이동 구간과 충돌)
    RewardLedger (사망/보상/회수 ID, 메모리 원장)
  WorldView (타일, 캐릭터, 적, 투사체, 드랍 표시)
    ActorView (스프라이트와 실제 동작 클립)
  HUD (조회와 명령 전달)
  Content (읽기 전용 Resource 정의와 에셋 매니페스트)
```

이 목록은 책임 경계이며 모두 전역 매니저로 만들라는 뜻이 아니다. E0에는 autoload를 두지 않는다. GameRoot가 실제로 필요한 객체만 생성해 참조를 전달한다. 함수 단위로 충분한 계산에 별도 서비스를 만들지 않는다. 공통 규칙은 가능한 한 SceneTree 없는 RefCounted/정적 계산으로 시험하고, 엔진 물리/렌더는 Node 쪽에 둔다. GDScript 코드가 다른 엔진으로 그대로 이식된다는 보장은 없다.

### 전투의 단일 기준

- IDLE -> APPROACH -> WINDUP -> ACTIVE -> RECOVERY, 사망 시 DEAD. 실제 이동이 기본이고 중앙 고정 캐릭터로 대체하지 않는다.
- AttackDefinition에 준비/발동/회복 시간과 클립 매핑을 함께 정의한다. ActorState의 공격 ID/진행 시간을 전투와 ActorView가 함께 사용한다.
- 화면의 애니메이션 콜백과 별도 Timer가 각각 피해를 발생시키지 않는다. 유일한 피해 적용자는 CombatResolver다. 애니메이션을 숨겨도 규칙이 바뀌지 않는다.
- 공격 개시 때 방향/공격 ID를 고정하고 발동 시 유효 대상/거리/생존 상태를 다시 검사한다. 공격 ID와 대상 ID 쌍으로 중복 적용을 차단한다. 방 재시작/사망은 이전 실행 ID를 무효화한다.
- 플레이어 이동은 CharacterBody2D 기반의 월드 충돌을 사용한다. 적 자동 접근과 로컬 간격 유지는 ActorController 책임이다. 큰 길찾기/군중 회피 프레임워크를 E0에 먼저 붙이지 않는다.
- 투사체는 발사 때 피해를 주지 않는다. 이전 위치부터 새 위치까지 이동 구간을 검사하고, 최초 충돌 후 만료한다. 그림의 수명은 판정 수명과 구별한다.
- 피해/사망 후 이벤트를 모아서 처리해 중첩 콜백으로 사망과 드랍이 반복되지 않게 한다. 전역 무제한 이벤트 버스는 만들지 않는다.

### 아트 제작 선택

첫 전사는 몸+무기가 한 세트인 프레임 애니메이션이다. 이미 무기가 있는 그림 위에 별도 검을 추가하지 않는다. idle/walk/attack/hit/death 클립, 방향, 발 피벗, 발동 프레임, 반복 여부를 에셋 매니페스트에 명시한다. ActorView가 같은 공격 진행 시간으로 SpriteFrames의 프레임을 선택한다. AnimationPlayer는 필요할 때 부가 연출에만 사용하고 별도 피해 시계를 만들지 않는다.

최초 시험은 4방향 읽기 쉬운 픽셀 캐릭터를 목표로 한다. 실제 채택할 팩의 방향/프레임과 재배포 라이선스를 먼저 확인한다. 부족한 클립은 미완료로 표시하며 정지 원화의 회전/확대/찌그러뜨리기로 통과시키지 않는다. 무기/아바타 외형 교체는 나중에 별도 분리형 제작 시험을 거친다. 일체형 첫 세트의 한계는 외형 교체 시 추가 아트가 필요하다는 점이다.

### 데이터와 확장

직업/적/공격/아이템/어픽스 정의는 Resource/.tres에 둔다. 공유 정의 리소스에 체력/현재 쿨다운을 기록하지 않는다. 실제 개체의 상태는 별도 인스턴스에 둔다. [S4]

보상은 사망 ID -> 드랍 ID -> 회수 ID로 추적한다. E0는 메모리 원장만 쓰며 실제 save.json은 읽지 않는다. 시각효과가 사라져도 회수 가능한 규칙상 드랍이 없어지지 않는다. 저장 도입 시 지급/회수/저장을 원자적 동작으로 설계하며 이것은 아직 구현하지 않는다.

나중에 도감은 사망/수집 이벤트, 펫은 보조 Actor, 어픽스는 전투 수정자, 원정 선택은 세션 한정 수정자로 붙인다. 계정 영구 진행과 원정/시즌 진행은 분리한다. 유료 결제/가챠/공식 래더는 별도 서버 권위와 검증이 필요한 후속 설계이며 현재 로컬 파일을 신뢰하는 온라인 순위표를 만들지 않는다.

## 4. 구현 순서와 테스트

다음 작업은 새 PR의 E0-C01: 독립 프로젝트 + 전사/근접 적의 실제 동작 세트 + 자동 접근/공격/피격/사망이다. 원거리 적/실제 투사체/드랍 회수를 E0-C02로 이어서 완성한다. 이후 E0-C03에서 40적 x1을 측정한다. 펫/가챠/환생 UI를 끼워 넣지 않는다.

풀링은 반복 생성되는 투사체/짧은 효과부터 고려한다. 모든 객체를 ECS로 재작성하거나 대규모 프레임워크를 먼저 만들지 않는다. 매 개체의 매 프레임 전체 적 검색을 피하고 목표 재검색 빈도를 제한한다. 공간 격자는 부하 로그가 필요성을 보이면 추가한다.

기능 자동검사, 실제 렌더, Windows 사용자 플레이, 성능 기록을 별도 상태로 남긴다. 첫 목표는 40적 x1에서 p95 16.7ms/p99 33.3ms다. 달성한 측정값이 아니다. 150/300적, x2/x5는 별도 조건이다. 시뮬레이션 배속과 측정 벽시계를 분리한다. 동일 시드를 썼다고 엔진 물리의 완전한 결정성이 증명되는 것은 아니다.

엔진 선택은 완료했다. 이후 다시 검토할 조건은 선택 버전의 재현 가능한 결함, 목표 부하에서 엔진/필수 도구 병목이 확인된 경우, 반드시 필요한 플랫폼/제작 도구 요구가 새로 정해지는 경우다. 막연한 불안이나 미완료 원화를 이유로 매 턴 선택을 다시 열지 않는다.

## 5. 사용자 로컬 작업

Godot 4.7.2-stable의 Windows x86_64 일반판을 별도 폴더에 압축 해제한다. .NET/mono판은 이번 선택이 아니다. 4.3은 삭제하지 않는다. 새 엔진으로 기존 D:\github\affix\project.godot을 열거나 변환하지 않는다. 새 독립 프로젝트가 생성되면 정확한 별도 폴더/브랜치와 F5 실행 절차를 제공한다. 이번 문서 작업을 위해 pull/switch하거나 백업 보고서를 다시 보낼 필요는 없다.

공식 릴리스: https://github.com/godotengine/godot-builds/releases/tag/4.7.2-stable
