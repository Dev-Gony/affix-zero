# 과거 개발 회고 | 텍스트 전용

목적: 실패를 설명할 수 있는 포트폴리오 기록을 유지하되 과거 코드·이미지·원본 ZIP을 현재 구현에 보관하지 않는다. 이 문서는 현재 개발 명세가 아니다. 증거가 확인되지 않은 수치와 성공을 새로 만들지 않는다.

## 경과

Godot에서 자동사냥·장비·스킬·환생·펫을 확장했으나 실제 동작/가독성/보상 표시가 사용자 기대와 달랐다. 이후 독립 E0의 단순 전투와 성능 fixture를 만들었지만 사용자에게 필요한 게임 화면을 대표하지 못했다. V0에서 이전 아틀라스를 재사용한 방향도 거절됐다. 사용자는 아트 전면 삭제, 다음으로 코드 전면 폐기와 Unity 재시작을 명시했다.

과거 검증 기록에서 이미지57개 제거, 기존 엔진 파일178개 제거를 확인했다. 이 수치는 당시 삭제 감사의 결과이며 현재 Unity의 플레이 완성도와 무관하다. 기존 코드가 새 트리에 남지 않도록 했지만 Git 과거와 로컬 폴더는 별도 정리 대상이다.

## 문제와 학습

| 문제 발생 지점 | 원인 분석 | 해결 방법 및 적용된 코드 개념 | 배운 점 |
| --- | --- | --- | --- |
| 기능 수는 늘었지만 전투가 읽히지 않음 | 실제 아트·동작 수락보다 시스템 확장이 앞섬 | 새 구현은 영웅1/적1의 동작 승인부터 진행 | MVP 범위 축소는 경험의 완성 기준과 함께 해야 한다 |
| 정지 그림 변형을 프레임 애니메이션처럼 설명 | 표현 구현과 프레임 에셋 검수를 혼합 | 실제 Sprite 배열/impact/출처 검사 및 시각 승인 분리 | 다른 프레임이 있는지와 제대로 보이는지는 둘 다 필요하다 |
| 테스트 PASS를 제품 완성으로 확대 | 코드/리소스/렌더/플레이 검증 경계를 흐림 | 검증 범위를 상태와 로그에 명시 | PASS에는 실행한 환경과 계약이 따라야 한다 |
| 성능 fixture가 게임 개발 진척을 대신함 | 기술 지표를 실제 사용자 경험보다 먼저 보여줌 | 실제 플레이 화면을 우선하고 성능은 이후 대표 부하로 측정 | 빠르게 그린 테스트 화면이 좋은 게임이라는 뜻은 아니다 |
| project.godot 동기화가 반복 중단 | 에디터가 변경한 설정과 원격 파일이 충돌 | 새 Unity를 별도 clone하고 .meta를 명시 추적 | 도구 설정·작업 경로·메타데이터도 개발 설계다 |
| 거절된 아트가 계속 복원됨 | 보존과 재사용을 구분하지 않음 | 과거는 텍스트 회고만 남기고 새 리소스만 검수 | 기록을 남기는 것이 실패한 자산을 다시 쓰라는 뜻은 아니다 |

## 면접에서 설명할 범위

실제 했던 문제 발견과 의사결정, 검사 범위, 사용자 피드백에 따른 재시작을 설명한다. 엔진 결함이나 바이러스 감염이 증명됐다고 말하지 않는다. 새 Unity는 아직 아트/에디터 플레이 검증 전이며 성능/출시 성공을 만들어 쓰지 않는다.
