# 과거 자료 정리 / 텍스트만 남기는 보존 정책 v0.2

## 결정과 현재 실행 범위

사용자는 과거 작업이 용량을 많이 차지하면 삭제하고 문서로만 기록하는 방식을 제안했다. 현재 프로젝트에서는 이미 옛 코드/이미지 사본을 보관하지 않는다. 이번에는 텍스트 회고와 읽기 전용 용량 검사 도구를 작성했다. **사용자 PC의 실제 용량은 아직 미측정이며 폴더·Git 이력·세이브 삭제는 수행하지 않았다.**

과거 파일의 존재만으로 바이러스 감염이나 Unity의 자동 오염을 진단할 근거는 없다. 실제 관리 문제는 오래된 코드/이미지/지침을 잘못 참고·복사·실행하는 혼선이다. 이를 막기 위해 현행 코드와 회고의 역할을 분리한다.

## 남기는 것

- 현재 Unity의 Assets/Packages/ProjectSettings, 필요한 .meta, 새 사용 리소스의 라이선스.
- 현행 PRD·설계·로드맵·작업 절차·검증 결과.
- 과거에는 문제/원인/해결/학습/정확한 증거 구분만 텍스트로 남긴다.
- 개인정보가 든 세이브는 사용자가 별도로 삭제 결정하기 전 보호한다.

## 용량별 정리 대상

| 대상 | 제안 | 주의 |
| --- | --- | --- |
| 옛 affix-e0 worktree | 새 Unity 독립 확인 후 삭제 후보 | affix의 Git 디렉터리를 공유하므로 순서 필요 |
| 옛 affix 프로젝트 | 마지막에 삭제 후보 | 다른 worktree, stash, 미커밋 소스가 필요한지 먼저 확인 |
| 옛 .godot/cache/export ZIP | 이전 프로젝트 폐기 후 정리 후보 | 새 프로젝트/현재 팩/개인 저장과 구별 |
| 새 Unity Library/Temp | 꼭 공간이 필요할 때 재생성 가능한 캐시 검토 | 에디터 종료 필요, 다음 import가 오래 걸릴 수 있음 |
| 새 Unity Assets와 .meta | 유지 | 캐시로 오인해 삭제하지 않음 |
| 새 저장소 .git | 유지 | 이력 크기와 작업 파일 크기는 별개 |
| AppData의 옛 게임 저장 | 별도 사용자 승인 전 유지 | 저장 삭제는 코드 정리의 필수 조건이 아님 |

## 실제 삭제 전 통과 조건

새 Unity가 독립 clone인지 확인한다. `git.common_dir`가 옛 affix 아래에 있다면 삭제를 진행하지 않는다. 새 프로젝트 import/메뉴가 정상인지 확인하고, 옛 작업의 modified/untracked/stash를 사용자가 포기해도 되는지 확인한다. 회고 문서를 새 저장소에서 열 수 있어야 한다.

모든 조건을 확인한 뒤 옛 linked worktree를 먼저 공식 `git worktree remove` 절차로 제거하고, 다른 연결이 없을 때 부모 저장소를 마지막으로 정리한다. 강제 옵션과 삭제 스크립트는 이번에 제공/실행하지 않는다. 주 디렉터리를 먼저 지우면 linked worktree의 메타데이터가 끊길 수 있다.

## Git 이력과 용량

새 브랜치에서 이미지를 삭제해도 과거 commit의 blob은 이력에 남을 수 있다. 일반 clone은 그 이력을 받아 용량을 사용할 수 있다. 아직 새 프로젝트를 복제하지 않았다면 `--depth 1 --single-branch --no-tags`로 현재 상태 위주로 받는다. 이미 로컬 변경이 있는 새 저장소를 지우고 다시 만들지는 않는다.

원격 과거 코드까지 완전히 제거하려면 별도 새 저장소 또는 이력 재작성/브랜치 정리가 필요하다. 이는 로컬 공간 정리와 다른 작업이며 사용자 명시 승인 없이 force-push/remote branch 삭제를 하지 않는다. 현재 원격 이력은 유지된다.

## 측정 도구의 한계

Inspect-Storage는 논리적 파일 길이 합계와 Git object 정보를 출력한다. 압축·하드링크·파일시스템 효과 때문에 실제 확보 공간과 정확히 같지 않다. PARTIAL 결과는 하한값이다. 폴더당 60초/250000개 항목 제한과 junction/symlink 비추적을 적용한다. 실제 결과 전 절감 GB를 기재하지 않는다.
